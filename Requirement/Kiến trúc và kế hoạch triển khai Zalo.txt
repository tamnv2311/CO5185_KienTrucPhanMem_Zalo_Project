Kiến trúc và kế hoạch triển khai Zalo-lite cho nhóm 3 người

Với đề bài này, nên chọn microservices vừa phải (5-6 service), giao tiếp event-driven, và polyglot persistence. Cách này vừa đủ “đất” để áp dụng nhiều giải pháp kiến trúc trong báo cáo, vừa không quá nặng cho 3 người trong khoảng 9 tuần.

1. Kiến trúc tổng thể
 [Web/Flutter Client]
        │ HTTPS (REST)            │ WSS (WebSocket/STOMP)
        ▼                         ▼
 ┌──────────────────────────────────────────┐
 │  API Gateway (Spring Cloud Gateway)      │  JWT verify, rate limit, routing
 └──────────────────────────────────────────┘
   │          │           │          │            │
   ▼          ▼           ▼          ▼            ▼
 User/Auth   Group      Chat       Media       Statistics
 Service     Service    Service    Service     Service
 (MySQL)     (MySQL)    (MongoDB   (MinIO/S3   (MySQL
                        + Redis)   + metadata)  aggregates)
   │          │           │          │            ▲
   └──────────┴───────────┴──────────┴────────────┘
                  Message Broker (RabbitMQ/Kafka)
                  events: user.registered, group.created,
                  message.sent, media.uploaded, ...

Thành phần và lý do chọn:

Thành phần	Công nghệ	Vai trò
API Gateway	Spring Cloud Gateway	Điểm vào duy nhất, xác thực JWT, rate limiting, routing
User/Auth Service	Spring Boot + MySQL	Đăng ký, đăng nhập, profile, danh sách bạn bè, phân quyền
Group Service	Spring Boot + MySQL	Tạo nhóm, thành viên, vai trò (owner/admin/member)
Chat Service	Spring Boot + WebSocket (STOMP) + MongoDB + Redis	Chat 1-1 và group, lưu tin nhắn, trạng thái sent/delivered/seen, presence
Media Service	Spring Boot + MinIO (hoặc S3)	Upload image/video/document, presigned URL, thumbnail
Statistics Service	Spring Boot + MySQL	Consume event, tổng hợp số liệu, API dashboard
Broker	RabbitMQ (đơn giản) hoặc Kafka	Tách rời service, phục vụ thống kê bất đồng bộ
Redis	Redis	Presence online/offline, cache, pub/sub để scale WebSocket
Frontend	Angular/React (web) hoặc Flutter	Màn hình login, danh sách chat, khung chat, quản lý nhóm, dashboard

Vì sao polyglot persistence: tin nhắn là dữ liệu ghi nhiều, dạng document, phân trang theo thời gian, nên hợp MongoDB. Tài khoản và nhóm có quan hệ chặt, cần transaction, nên dùng MySQL. Presence và cache dùng Redis.

2. Các quyết định kiến trúc quan trọng (ADR)

Mỗi quyết định nên viết thành một ADR ngắn để đưa vào báo cáo.

Database per service: mỗi service sở hữu dữ liệu riêng và không join chéo DB.
Giao tiếp: REST cho truy vấn đồng bộ, event qua broker cho thống kê và thông báo.
Thống kê theo CQRS đơn giản: Chat/User/Media chỉ phát event, Statistics tự consume và lưu bảng tổng hợp theo ngày. Truy vấn dashboard không ảnh hưởng hiệu năng chat.
Thứ tự và độ tin cậy tin nhắn:
Mỗi conversation có số thứ tự seq tăng dần.
Client gửi kèm clientMsgId để idempotent, tránh trùng khi retry.
Trạng thái sent → delivered → seen.
Scale WebSocket: nhiều instance Chat Service dùng Redis pub/sub hoặc broker relay để đẩy tin đến đúng người đang kết nối ở instance khác.
Media: client upload thẳng lên object storage bằng presigned URL, không đi qua service (giảm tải). Service chỉ lưu metadata và giới hạn loại/kích thước file.
Bảo mật: JWT access token ngắn hạn + refresh token, mã hóa mật khẩu bằng BCrypt, kiểm tra quyền thành viên trước khi đọc/gửi tin nhắn nhóm.
Resilience: dùng Resilience4j (timeout, retry, circuit breaker) cho lời gọi giữa các service.
Triển khai: Docker từng service, Docker Compose cho môi trường dev và demo, GitHub Actions cho CI/CD, deploy lên cloud (VPS, AWS, Azure hoặc GCP free tier). Với 3 người, một VM chạy Docker Compose là đủ; Kubernetes chỉ nên trình bày như hướng mở rộng.
Observability: log tập trung có traceId, Spring Actuator + Prometheus/Grafana (có thể làm nhẹ).
3. Mô hình dữ liệu tóm tắt
MySQL – User: users(id, phone/email, password_hash, display_name, avatar, status), friendships(user_id, friend_id, status)
MySQL – Group: groups(id, name, owner_id, avatar), group_members(group_id, user_id, role, joined_at)
MongoDB – Chat: conversations(id, type[1-1|group], members[], lastMessage), messages(id, conversationId, seq, senderId, type[text|image|video|doc|emoji], content, mediaRef, status, createdAt)
MySQL – Stats: daily_user_activity(date, user_id, msg_count, media_count), daily_system_stats(date, total_msg, active_users, new_users), group_activity(date, group_id, msg_count)
4. Phân công 3 thành viên

Chia theo mảng chuyên trách để mỗi người sở hữu một phần chạy được từ đầu đến cuối.

Thành viên	Vai trò	Phụ trách

6. Ánh xạ sang nội dung báo cáo

Phần “giải pháp đã học áp dụng cho đề tài” nên đi theo cấu trúc sau:

Requirement và quality attributes: scalability, availability, performance (độ trễ tin nhắn), security, modifiability, testability, kèm tactic tương ứng.
Kiểu kiến trúc: microservices, API Gateway, event-driven, CQRS (phần thống kê), layered trong từng service (Controller-Service-Repository).
Design pattern: Observer/Pub-Sub (chat), Strategy (xử lý theo loại tin nhắn), Factory (tạo message), Adapter (storage), Circuit Breaker, Idempotent Consumer.
Mô tả kiến trúc: C4 (Context, Container, Component), sequence diagram cho luồng gửi tin nhắn và upload media, deployment diagram.
Dữ liệu: lý do chọn MySQL/MongoDB/Redis, chiến lược index và phân trang.
Triển khai: Docker, CI/CD, môi trường cloud, release hàng tuần.
Kiểm thử và đánh giá: kết quả load test, so sánh với quality attributes đã đặt ra.
Phân công và nhật ký tuần: bảng nhiệm vụ, đóng góp từng thành viên.
7. Gợi ý cắt giảm nếu thiếu thời gian

Thứ tự ưu tiên khi cần cắt: (1) giữ trọn chat text + group + image, (2) video và document có thể chỉ upload và tải về, không cần streaming, (3) bỏ push notification, dùng realtime khi đang online, (4) bỏ Kafka, dùng RabbitMQ, (5) mobile chỉ làm nếu dư thời gian, ưu tiên web.

Bạn muốn mình đưa phần này vào file Word/PDF, hoặc triển khai tiếp phần nào (sơ đồ C4, OpenAPI contract, cấu trúc repo và Docker Compose mẫu)?

Cấu trúc code chi tiết (monorepo)

Mình chọn monorepo + Maven multi-module cho backend (Spring Boot, Java 21) và React + TypeScript (Vite) cho web. Monorepo giúp 3 người dùng chung một CI, chia sẻ thư viện chung và dễ làm release theo tuần. Nếu nhóm quen Angular thì chỉ cần đổi thư mục frontend/web, phần còn lại giữ nguyên.

8. Quy ước chung
Hạng mục	Quy ước
Package Java	com.zalolite.<service>.<layer>
Port	gateway 8080, user 8081, group 8082, chat 8083, media 8084, stats 8085
Header nội bộ	Gateway verify JWT rồi gắn X-User-Id, service nội bộ tin header này
API prefix	/api/<domain>/..., API nội bộ dùng /internal/... (không expose ra gateway)
Branch	main (ổn định), develop, feature/<service>-<mô tả>, release/wN
Commit	Conventional Commits: feat(chat): add seen receipt
Exchange RabbitMQ	zalolite.events (topic), routing key dạng user.registered, message.sent
Queue	<consumer>.<event>, ví dụ stats.message.sent
Database	user_db, group_db, media_db, stats_db (MySQL), chat_db (Mongo)
9. Thứ tự tạo code theo tuần
Tuần 3 (A): pom.xml gốc, libs/*, docker-compose.infra.yml, khung từng service chỉ có Application và /actuator/health, CI. Khi đó mọi người clone về là chạy được.
Tuần 4: user-service, api-gateway, màn hình auth ở frontend.
Tuần 5: group-service, friends và groups ở frontend, WebSocket handshake ở chat-service.
Tuần 6-8: chat-service đầy đủ, media-service, các component trong features/chat.
Tuần 9: statistics-service, features/stats.
Tuần 10: tests/, infra/monitoring.

Phân chia quyền sở hữu thư mục: A giữ libs/, api-gateway, user-service, group-service, infra/, .github/. B giữ chat-service, media-service. C giữ statistics-service, frontend/, tests/. Tài liệu docs/ ai làm phần nào thì viết phần đó. Có thể ghi sẵn điều này vào CODEOWNERS.
